# GitHub deployment and migration

## Canonical source

Repository: https://github.com/calbogdanov-dotcom/intro-maker
Production branch: `main`.

Work on branches and use pull requests. The GitHub commit is the deployment input. Local checkouts are for editing and testing. A GitHub collaborator who can merge into `main` can trigger a deployment once automatic deployment is connected; sharing a personal hosting password is unnecessary.

## Prepared Render configuration

- Connect the repository using Render's GitHub integration.
- Create a Blueprint using `render.yaml` from the repository.
- One Node 22 service in Frankfurt, smallest paid compute tier, one 1 GB disk.
- Build: `node scripts/build.mjs`; start: `node server/index.mjs`.
- Deploy `main` after GitHub CI passes.
- Data: `/var/data/intro-maker`, on the mounted persistent disk.
- Shared editing: enabled to match the current live project. Any visitor can edit and publish.
- Owner password: generated by Render, stored in hosting environment settings; required for comment moderation.
- Initial origin: Render's automatic HTTPS URL, via `RENDER_EXTERNAL_URL`.
- Custom origin later: explicit `INTRO_MAKER_ORIGIN`.

Provider account connection, billing approval, and actual provisioning are separate from preparing this file. No deployment is established just by committing the Blueprint. Do not use ephemeral storage for live media and comments. This is a single-instance application.

## Existing live site

The current hosted instance is separate from this portable repository. Before replacing it, reconcile features added to the live source since the public package was made. Keep the version 1 animation renderer and review identities intact. Production branding and client artwork must remain separate from the public sample assets.

1. Create a new service at its temporary Render URL while the existing domain continues serving the current site.
2. Back up every live object, including metadata, private libraries/drafts, publication boards, recordings/audio, comments, removal receipts/hashes, and removal markers. Preserve all object keys and iteration/slot/comment identities. Do not commit this backup to GitHub.
3. Prepare and verify a lossless import into the disk-backed object store. Preserve HTTP content types and logical JSON values. Record counts and checksums before and after import; validate references from both boards.
4. Configure production branding and owner access. Verify shared editor access, same-origin write checks, owner-only moderation, unpublished board media restrictions, both review types, old feedback, and browser recording/publication.
5. Freeze writes briefly, copy the final changes, and check counts/checksums again. Keep the backup and original deployment available for rollback.
6. Add the custom domain on the new host, configure the canonical HTTPS origin, and change DNS only after the new copy is verified. Test HTTPS, old share links, media seeking, sign-in, and comment persistence.
7. Merge a small verified change into `main` and confirm deployment of that exact GitHub commit. Confirm that uploads, presets and comments persist through redeployment.

DNS cutover must wait until data migration and production verification are complete. Never run two writable instances against the same disk directory.

## Operating after cutover

- Merge to `main` to deploy after CI succeeds.
- Use a revert commit for code rollback; do not replace data with an old snapshot as a routine code rollback.
- Back up data separately from GitHub source.
- Increase disk capacity before it fills; published video can consume space quickly.
- Hosting team membership is optional for code-triggered deployment, but needed for direct service administration.
